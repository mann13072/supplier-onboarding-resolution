This file records the intended repository presentation and the remaining publication steps. Preparing these files does not create a remote repository, push code, deploy the app, or create a public release.

The GitHub owner and final visibility are selected at publication time. No credentials or private email address belong in this document. Git commit author information becomes public when commits are published; review the locally configured identity or use an appropriate GitHub no-reply address before the first commit.

## What belongs in the repository

- Application source, tests, lockfile, and dependency manifests.
- README, architecture, demo guide, contribution/security guidance, and changelog.
- MIT license, Git attributes, editor settings, runtime version hints, and CI workflow.
- The two approved synthetic screenshots in `docs/assets/`.

## What stays local

`node_modules/`, `dist/`, `.venv/`, `data/`, SQLite files, logs, environment files, caches, and test captures are ignored. Do not force-add them. The real API credentials or enterprise integrations described as future possibilities do not exist in this project.

## Before the first push

1. Review the README images and staged file list. Confirm only intended synthetic content is included.
2. Run `git diff --cached --check` and review `git diff --cached --stat`.
3. Confirm a fresh-clone setup builds the frontend and runs the backend tests.
4. Confirm the local browser walkthrough passes. The CI workflow cannot claim a hosted pass until GitHub runs it.
5. Review the Git author identity without changing global settings unnecessarily.
6. Choose the actual GitHub owner, repository name, and visibility. Create an empty remote repository to avoid competing autogenerated README/license files.
7. Create the initial commit, add the verified remote, and push `main`.
8. Inspect README rendering, image links, Mermaid diagrams, license detection, and the first Actions run on GitHub.
9. Set the description and topics. Add a homepage only if an application is genuinely hosted.

These are publication instructions, not a record that the steps have been completed.

## Hosting is a separate task

Pushing this source to GitHub does not make the application usable online. GitHub Pages cannot run the Python backend or persist SQLite workflow state. The included workflow builds and tests; it does not deploy.

A hosted multi-user demonstration would need a deliberate deployment design, isolated demo sessions or reset behavior, authorization, and storage choices. That work is not part of this preparation.
